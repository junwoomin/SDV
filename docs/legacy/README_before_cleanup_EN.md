`./start.sh` preserves independently started CARLA and training processes. The app stops only its own engines. It reuses a prepared `.venv-web` unless `SDV_WEB_PYTHON` explicitly selects another interpreter; existing CARLA paths can be selected in Settings.

Open **http://127.0.0.1:8765**. Python **3.7, 3.8, 3.9 and 3.10** are supported; newer Python remains supported. The launcher uses your active Python, creates a separate `.venv-web`, and installs version-compatible web dependencies without changing research CUDA/PyTorch/NumPy packages. If an existing web environment uses another Python version, it is preserved and a `.venv-web-pyXY` environment is created. Updated requirements are applied automatically. The frontend and API are served from one local Python process; Node.js and external CDNs are not required. Select the existing CARLA/PyTorch interpreter in Settings.

In **Simulation**, **Install & start CARLA** first installs `carla==0.9.15` only when the selected research Python has no CARLA package, verifies the import and client version in that same interpreter, then downloads the engine if needed, starts it, and connects when RPC is ready. **Install only**, cancellation/resume, engine stop, and logs are also available. The installer uses `carla/`, downloads 8,386,636,048 bytes (about 7.81 GiB), and initially requires 45 GiB of free space; existing partial downloads reduce the remaining space requirement. An existing external server can still be connected separately. Client installation uses a binary wheel without dependencies; CUDA, PyTorch and NumPy are unchanged. A different or broken existing CARLA client produces an error instead of being overwritten. **Install only** downloads the engine without requiring Python CARLA packages. Old or missing pip is handled with a cached pip 24.0 wheel runner without upgrading research pip.

In **Simulation → Sensors**, edit sensor positions numerically or drag them in the top/side placement diagrams. Diagram dots show approximate sensor positions; use the numeric coordinates and real RGB/LiDAR preview to check the placement. Start the preview, then **Apply to preview** to check draft changes before saving. Sensor frames come from a separate process using the selected research Python (`carla`, NumPy and Pillow required). Applying a draft does not save the collection configuration; use **Save sensor settings** when ready.

Sensor configuration previews retain only the latest JPEG. The requested rate defaults to **24 FPS** and accepts integers from **1–60 FPS**; actual delivery depends on the CARLA simulation rate, GPU, encoding and transfer performance. RGB preview capture is capped at 640 pixels on its longest side. Collection image resolution stays unchanged. The preview uses the current CARLA world/map without loading a map or changing world settings. It ticks only an app-owned synchronous server; an external synchronous server needs its own ticker. Stopping the preview removes only the actors it created. Collection/training, engine stop and connection/interpreter changes are blocked until the preview stops. The separate **collection preview** reads saved camera/BEV frames and is empty until data has been saved.

In **Training**, unavailable input sensors and output tasks are gray and disabled, with a reason based on the selected train/validation paths and camera inputs. Missing mandatory conditions appear in red. Every scene must contain aligned frame IDs; partial data does not enable a choice. BEV accepts one or more selected cameras; actual labels and calibration are checked. When BEV is off, its decoder is `None`, using the original model's existing forward branch. File availability does not replace the full calibration, dimensions, dependency and CUDA preflight.

The training **Check readiness** action prepares the selected encoder's official pretrained file in the background: the official checkpoint declared for that selected encoder in the shared model registry. It verifies the SHA256 prefix published in the upstream filename and reuses a verified file in `.runtime/cache/torch/hub/checkpoints/`. Progress and failures appear in the training panel. Existing invalid files are preserved and reported; no model packages are changed. Ordinary status reads do not start downloads. Recorded local validation (raw JSON is not published) covers actual downloads of both files and cache reuse without network access on Python 3.7; subsequent real CPU validation also loaded ResNet34, legacy EfficientNet-B0 and MobileNetV3 Small weights and ran finite forwards. On-host CUDA training smoke tests now pass; see the current training follow-up report. QA weights are not included in the project archive.

Training now has **Setup / Queue / Monitoring** tabs. Queue immutable model/data/calibration snapshots while another model runs, reorder waiting jobs, pause at the end of the current epoch, and resume from the next epoch with optimizer, scheduler, RNG and metric history restored. Queue deletion retains experiment results. Blocked jobs display their actual readiness requirements. ETA uses measured completed-epoch durations.

Monitoring records up to **four fixed validation samples** per dataset content, shared across model experiments. Validation predictions default to every epoch; fixed training-sample inference defaults to every 100 steps (0 disables it). Use horizontal Epoch/Step timelines for saved input/ground-truth/prediction history, or compare the same sample/task across experiments with matching validation dataset fingerprints. Real epoch metrics include segmentation IoU/accuracy/Dice, BEV IoU/Dice/precision/recall, depth errors/threshold accuracy, and detection AP/precision/recall. Direction-aware Best values include their epoch. Charts are about 1.5× taller and logs start collapsed. Result rows include optimizer and model parameters. See [training monitoring details](../TRAINING_MONITOR_KO.md) and the current validation scope.

The header **KO / EN** selector remembers your language in browser local storage and preserves form drafts when switching. User names, paths, experiment data and raw logs retain their original text. Refreshing or changing language does not stop server tasks.

The web console controls real collection/training subprocesses, stores job/configuration history in SQLite, displays real metrics, and inspects saved data. A shared sensor blueprint helper makes saved LiDAR parameters effective in both preview and collection; omitted fields retain legacy defaults. Hardware-free interface and process tests do not establish CARLA/GPU pipeline correctness. Existing CARLA 0.9.15 was reused for on-host engine, sensor, driving, collection and CUDA training validation. A fresh complete 8 GB download was not repeated. See the validation report before running a full experiment.
